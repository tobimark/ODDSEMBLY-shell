### 1.1 墨迹权重（本轮新增，贡献最大的单项修正）

参考帧是 **DirectWrite + ClearType（次像素/LCD）** 渲染，Chromium 在 `--disable-lcd-text`
下是灰阶 AA：**同一字形、同一字号，参考帧的墨迹覆盖率约多 25%**
（实测：字形框内平均亮度差 5–10 级，例如文件名行 ref 212.25 vs 原实现 217.19）。
用一发丝描边复现茎干加粗：

```ts
const EMBOLDEN = '0.28px currentColor';   // 所有文字统一 WebkitTextStroke
```

扫参：`0 / 0.22 / 0.25 / 0.28 / 0.31 / 0.34 / 0.42` → 2.71 / 2.29 / 2.28 / **2.27** / 2.28 / 2.27 / 2.64（其余相同）。
`text-shadow: 0 0 0.5px` 方案是 2.31，不如描边。
见 §9：这只能是近似，因为参考帧的加粗来自次像素渲染本身。

### 1.2 推进（advance）实测：CJK 与 ASCII 不同比例

参考帧是**次像素定位**，CJK 单元 35.75 原生 px、ASCII 17.86 原生 px；
Chromium 在 DPR2 下把推进量化到整设备像素（36 / 18），所以一整串字会累积漂移：

- 10 个汉字的文件名：右端比参考帧 **+2 原生 px**；19 字符的 ASCII 名：**+1 原生 px**
- 用 `letter-spacing` 补偿后，各行右端与参考帧完全重合（实测 ink 右端 427/355/248/248/499/499/480/499/462 全等）
- 注意单位：`letterSpacing: -0.15`（无 `px`）会被浏览器丢弃 → 立刻退化到 3.9 分，必须带单位

判定用两种方式互相印证：① 逐窗口亚像素互相关求局部漂移，对 x 拟合斜率
（CJK 行 0.0047 原生/原生，纯 ASCII 行 0.0002~0.0004）；② 整串墨迹宽度比。

### 1.3 文件图标：墨迹垂直居中，不是盒子居中（本轮新增）

参考帧里 **9 个文件图标的墨迹中心全部精确落在行中心**（原生 y = 587 + 56i），
而 `svg/fileIcons` 的 16×16 重建网格是"墨迹顶端对齐 + 各类墨迹高度不同"（python 1..14、
json 1..10、html 1..12、md 1..6…）。所以每类要补 `dy`：

| kind | python | json | image | svg | video | xlsx | html | md |
|---|---|---|---|---|---|---|---|---|
| dy(逻辑 px) | 0 | +2 | 0 | 0 | +2 | 0 | +1 | +4 |

修正前这 5 行图标的局部差分 43–57，修正后全部 **0.00**。
（同一规律解释了胶囊里图标的横向偏移 → 见 §4。）

### 1.4 图标盒子尺寸（本轮纠正）

`size` 一律按 **目标墨迹 / 资产墨迹 × 16** 反算，不要一律 16，也不要凭感觉放大：

| 图标 | 参考帧墨迹(原生) | 用值 | 修前 → 修后 |
|---|---|---|---|
| chevron-down ×2 | 18×10 | **13.75** | 14.5（墨迹 19×11，偏大 1） |
| folder / folder-plus | 30×26 | **16** | 17（墨迹 32×27，偏大 2） |
| search | 30×30 | **16** | 17（墨迹 30×32，偏高 2） |
| plus | 24×24 | 16 | 无需改（本就吻合） |
| clock / bolt / bot（胶囊） | 28×28 / 24×28 / 28×25 | 15 / 14.5 / 15 | 试过 14.5/14/14 → 更差，回退 |
| chart-bar / settings / bulb（chip） | — | 15 / 15 / 14.5 | 试过 14.3 → 更差，回退 |

改尺寸会同时改变墨迹在盒子内的落点，所以 **尺寸改了要跟着改盒子 top**（本轮 chevron +1 逻辑 px、
folder 系 +0.5 逻辑 px、search +0.5/+0.5）。

## 9. 残余问题（诚实清单，按影响排序）

1. **次像素 AA（不可消除，占剩余误差 ~90%）**
   参考帧是 ClearType/次像素渲染（字形边缘有蓝/橙彩边，实测 `mean|R−B| = 20.3`），
   而 `tools/shoot.mjs` 带 `--disable-lcd-text`，Chromium 只能灰阶 AA（`mean|R−B| = 12.7`）。
   发丝描边只补了"总量"，补不了"边缘的彩色分布"。
   **量化**：同一份代码换 `--enable-lcd-text` 截图（我另存了私有脚本，未改 `tools/*`），
   sidebar = **2.01**（灰阶 2.27）。也就是说渲染模式本身就值 0.26 分。
   如果 Lead 愿意改 `tools/shoot.mjs`（去掉 `--disable-lcd-text`，加 `--enable-lcd-text`），
   整个 CHROME 的分数都会一起降——但那是"改尺子"，需要 Lead 决定。
   **以灰阶为准的前提下，2.27 已接近该渲染模式的floor**：逐行最优时纯 ASCII 行 2.5–5.8、
   CJK 行 7.5–11，全部是边缘差。
2. **CJK 行仍然是误差最大的地方**（9–11 vs ASCII 2.5–5.8）。CJK 笔画更密，边缘占比更高，
   同样 0.5 原生 px 的次像素相位差会放大成更大的逐像素差。行 6（`数据统计-20260813.xlsx`）
   在同档 -0.15 下仍偏 11.04，单独给它 -0.11 能到 ~8，但我判断这是**逐行过拟合**，没写进去。
3. **bee 是手绘的**（应用资产表里确实没有 bee），墨迹框已对齐 28×28，内部笔画位置仍有差（局部 3.7）。
4. **胶囊图标形状差**：clock/bolt/bot 的墨迹框已对齐，但 bot 头部的圆角与天线在 2 倍图下仍有 1 原生 px 级
   的形状差（局部 4.8）。三个 chip 图标同理（局部 2.4）。
5. **斜纹 0.5 原生 px 相位差 + 缺 1 原生 px 的 #efefed 过渡带**：纯斜纹区差分 0.8–1.1，
   对总分贡献 <0.01，未继续拟合。
6. **投影/边框是拟合值**（卡片/胶囊/登录按钮 `box-shadow`），参考帧只能给模糊后的灰度。
7. **未做交互态**（hover/选中/滚动条）：参考帧只有静态一帧。
8. **卡片右缘半圆缺口**保留上一版实现（9×9 圆、`#f6f1ea`，left 251.5 / top 184.75），本轮未复测。
9. ⚠️ **并发编辑**：本会话期间 `src/regions/Sidebar.tsx` 至少被另一个进程改写过一次
   （23:08:14，加入了 dy 表、size 17、`letterSpacing -0.06` 等）。本轮最终值是在"以磁盘为准 + 重读再改"
   的前提下收敛出来的；如果后续还有人改这个文件，请重新跑 §7 的自测确认分数。

## 文件列表：从参考画面改为真实工作区（2026-11-17）

几何不变（图标 16×16 @ x16/top+8、文本 @ x38/top+6、裁剪 210px、28px 行距、区域 y 222–714 可滚动），只有**内容**改为数据驱动：

- 数据：`GET /api/fs/list?path=<相对路径>`，每个目录请求一次并按路径缓存；`.` 是工作区根。
- 路径由桥接统一成 `a/b` 形式（正斜杠、无尾分隔符）——同一个字符串同时是行 key、`@` token 和下一次 `fs/list` 的参数。
- 目录行显示 chevron（`chevron-right`/`chevron-down`），点击展开/收起并懒加载；文件行显示 `FileIcon` 位图，未知扩展名回退单色 `file` 图标。
- 图标纵向微调沿用实测表：`KIND_DY`（python 0 / json 2 / image 0 / svg 0 / video 2 / xlsx 0 / html 1 / md 4）。
- 点击文件 → `window.dispatchEvent(new CustomEvent('kunlun:mention-file', {detail:{path}}))`；`AgentPanel` 收到后把 `@path` 追加到输入框并聚焦，同时登记到 `knownPaths`，保证发送时成为真实附件。
- 新增 `.hide-scrollbar`（styles.css）：Chromium 下也能隐藏滚动条（之前只有 Firefox/IE 属性，headless 截图里看不到滚动条是因为 `--hide-scrollbars`）。
